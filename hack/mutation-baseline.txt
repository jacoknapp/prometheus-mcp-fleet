# Minimum Gremlins test efficacy per package, in percent. Read by
# hack/mutation.sh, which fails a package scoring below its entry.
#
# THESE ARE CONSERVATIVE FLOORS, NOT FINISHED WORK, AND NOT THE MEASURED SCORE.
#
# Each entry is the score from the first full sweep, floored to a whole percent
# and then reduced by 3. The margin is not padding -- it is the measured
# reproducibility of the tool. Efficacy is killed/(killed+lived), and a mutant
# that merely runs slowly is recorded as TIMED OUT rather than killed, so it
# leaves the numerator without leaving the denominator. How many mutants land
# in that bucket depends on how loaded the machine is. internal/hub, with the
# source unchanged, scored:
#
#     92.93%  (8 workers, no memory cap)    1 timed out
#     90.54%  (4 workers, no memory cap)   26 timed out
#     89.71%  (4 workers, 8G memory cap)   32 timed out
#
# A baseline set to the best of those would fail on any differently loaded
# machine, and a flaky gate teaches people to ignore the job. Three points
# covers the swing observed; a package that drops further has genuinely lost
# test strength.
#
# A package below 100 here has NOT had its survivors classified yet -- that
# work is per-package and ongoing. When you finish one, raise its number and
# record beside it the reason it stopped where it did. An equivalent mutant no
# test can kill is a legitimate reason; a test written to satisfy the tool
# rather than to describe the software is not.
#
# Lowering an entry needs a reason in the commit message.
